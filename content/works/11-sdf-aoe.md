Maze의 보스·몹 공격을 바닥에 미리 알려 주는 예고장판 시스템입니다. 겉보기엔 "장판 그리는 오브젝트 하나, 데미지 주는 콜라이더 하나"면 끝일 것 같지만 세 가지 조건이 붙으면서 설계가 전부 결정됐습니다.

![공격 예고장판 시연. 바닥의 장판이 빨갛게 차오르고 타격 순간 꽉 찹니다.](img/11-sdf-aoe/aoe-loop.mp4){w=360}

- **보이는 범위와 실제 맞는 범위가 1픽셀도 어긋나면 안 됐습니다.** 플레이어는 장판을 보고 피하니까 "안 닿았는데 맞았다"가 한 번이라도 나오면 게임이 무너집니다.
- **채움 애니 타이밍을 소수점까지 맞추고 싶지 않았습니다.** 아트·기획팀이 "장판이 꽉 차는 순간 = 맞는 순간"이 저절로 보장되길 원했습니다.
- **모바일에서 가벼워야 했습니다.** 안드로이드 타깃이라 장판이 동시에 여럿 떠도 오버드로우와 GC로 프레임을 깎으면 안 됐습니다.

## 1. 그리기와 판정을 하나의 데이터로

가장 먼저 정한 것은 **장판을 그리는 데이터와 데미지를 판정하는 데이터를 같은 하나로** 묶은 것입니다. 보통은 비주얼용 메시와 판정용 콜라이더를 따로 두는데 그러면 둘이 미묘하게 어긋납니다. 반경을 3.0으로 그렸는데 콜라이더는 2.9인 식입니다.

그래서 원·부채꼴·사각과 치수만 든 **순수 모양 데이터(TelegraphShape)** 를 하나 두고, 이 똑같은 데이터를 셰이더에 넘겨 그리고 같은 데이터의 "이 점이 안에 있나" 판정으로 플레이어를 검사하게 했습니다.

```
              모양 데이터 (원 / 부채꼴 / 사각, 치수만 든 순수 struct)
                     │                              │
           "이 모양대로 그려줘"            "이 점이 이 모양 안이야?"
                     ▼                              ▼
              셰이더가 렌더                    Contains() 로 데미지 판정
```

셰이더는 이 데이터로 모양을 수학적으로 그려서 해상도에 무관하게 테두리가 선명합니다. 무엇보다 그리는 코드와 때리는 코드가 **물리적으로 같은 숫자**를 보니 어긋날 방법이 없습니다. 반경을 바꾸면 비주얼과 판정이 동시에 바뀝니다. "그린 범위 = 맞는 범위"를 구조로 못 박은 것입니다.

![실제 인게임 장판. 셰이더로 그린 사각 장판이 선명한 테두리로 뜨고 그 범위 안에 플레이어가 서 있습니다. (좌상단 60 FPS — 모바일에서도 가볍게 동작)](img/11-sdf-aoe/fig01-ingame.png){w=420}

## 2. '꽉 참 = 타격'을 강제했다

다음은 타이밍입니다. 장판은 시간에 따라 빨간 게 차오릅니다.

```
fill = (지금시각 - 시작시각) / 지속시간      // 0 → 1 로 차오름
```

순진하게 만들면 함정에 빠집니다. 애니메이션의 실제 타격 프레임이 0.83초인데 장판 지속시간을 0.8초로 잡으면 **장판은 꽉 찼는데 아직 안 때리는** 0.03초가 생깁니다. 플레이어 눈엔 "다 찼는데 왜 안 맞지" 혹은 반대로 "덜 찼는데 맞았어"가 됩니다. 이걸 소수점까지 맞추는 것보단 더 좋은 방법이 없을까 생각했습니다.

그래서 타이밍을 맞추는 대신 **타격 순간에 장판을 강제로 100%로 스냅**했습니다.

```
스킬이 실제로 때리는 그 프레임 → 완료 호출
   → fill 을 즉시 1.0 으로 스냅
   → 0.1초 '꽉 찬 채로' 플래시 → 반납
```

완료를 부르는 순간이 곧 타격 순간이니 **"장판이 꽉 차는 걸 본 순간 = 맞는 순간"** 이 코드 구조상 항상 참이 됩니다. 공격이 중간에 끊기면(그로기·사망) 취소로 조용히 지웁니다. 이 표시→완료 / 표시→취소 생명주기를 개별 공격마다 짜지 않고 장판을 띄우는 공통 경로에 한 번만 심어 뒀기 때문에, **완료·취소 두 출구가 모든 장판에 적용됩니다.** 장판을 한 번 띄우면 두 출구가 자동으로 따라옵니다.

## 3. 그리는 서비스와 때리는 주체를 분리했다

장판을 그렸으면 누가 언제 데미지를 줄까요. 여기서 길이 둘로 갈립니다. 핵심은 그리기 서비스(TelegraphManager)는 **데미지를 하나도 주지 않고**, 때리는 건 항상 공격자 쪽이라는 분리입니다.

- **방법 A — 디자이너용, 코드 0줄.** 몹에 컴포넌트를 붙이고 공격 클립의 windup 프레임에 애니 이벤트 하나만 꽂으면 끝입니다. 장판을 표시하고 그 순간의 모양·위치·회전·타격시각을 스냅해서 예약합니다. 예약 시각에 플레이어가 범위 안이면 타격이 들어갑니다.
- **방법 B — 코드 주도, 정밀 제어.** 이동·무적·넉백이 얽힌 보스는 상태 클래스가 표시·완료·판정을 직접 지휘합니다.

포인트는 **그린 그 순간의 위치·회전을 박제**한다는 것입니다. 몹이 그새 움직여도 판정은 처음 그린 그 자리에서 납니다. "장판은 여기 그려놓고 저기서 때리는" 변수가 없습니다. 두 방법 다 같은 매니저와 같은 모양 데이터를 씁니다. 위(그리기 서비스)는 공유하고 아래(판정 주체)만 다른 것입니다.

## 4. 보스는 장판으로 회피를 강요한다

방법 B의 포인트는 한 보스의 **점프 내리찍기**입니다. 여기서 장판은 단순한 경고가 아니라 **회피 타이머**입니다.

```
[Enter]  점프 시작 순간, 플레이어 위치를 착지점으로 고정
         체공시간 == 장판 채움시간 == 회피 윈도우

[Air]    보스는 솟구쳐 플레이어 머리 위로. 그동안 장판은 차오름.
         플레이어: "장판 꽉 차기 전에 회피기를 써야 한다"

[Land]   완료 호출 → 장판 100% 스냅 = 타격 순간
         Contains(착지점, 플레이어) → 안에 있으면 타격 + 넉백
```

**체공 시간을 장판 채움 시간과 똑같이** 맞췄기 때문에 장판이 차오르는 속도가 곧 "언제까지 피해야 하는지"를 플레이어에게 정직하게 알려 줍니다. 앞의 완료 스냅 덕에 착지하는 바로 그 프레임에 장판이 꽉 차고 판정이 납니다.

규칙 하나를 더 걸었습니다. 회피·무적 스킬 중이면 타격이 무효를 돌려주고 그러면 넉백도 걸리지 않습니다. 즉 장판은 "제때 피하면 완전 무효, 못 피하면 데미지와 넉백"을 만들어 **회피기를 쓰게 유도하는 장치**가 됩니다.

## 5. 모바일을 위해 전부 재활용했다

마지막 조건은 모바일에서 여러 장판이 떠도 무겁지 않아야 한다였습니다. 그래서 매니저가 **아무것도 새로 만들지 않게** 했습니다.

```
초기화 시 쿼드 8개를 미리 만들어 풀에 재움 (SetActive false)
표시   → 비활성 슬롯 하나 깨워 재사용 (없으면 가장 오래된 것 뺏음)
채움   → 새 오브젝트 생성 0. MaterialPropertyBlock 으로 색·fill만 교체
끝나면 → 파괴 안 함. 다시 풀에 반납
```

- **런타임 할당 제로** — 게임 도중 생성·파괴가 없어 GC 스파이크가 없습니다.
- **머티리얼 인스턴스 제로** — 색·채움은 MaterialPropertyBlock으로만 바꿔 머티리얼이 복제되지 않고 드로우콜 병합이 유지됩니다.
- **동시 표시 상한 = 풀 크기** — 넘치면 가장 오래된 장판을 재활용해 화면이 장판으로 뒤덮여도 비용이 고정입니다.

무거운 최적화 기법이 아니라 "만들지 말고 돌려쓴다"는 원칙 하나입니다.

## 6. 전체 흐름

```
[공격자 — 장판을 요청]
   방법 A: 애니 이벤트로 표시       방법 B: 보스 상태가 직접 호출
        │   둘 다 넘기는 건 모양 데이터 하나 (원/부채꼴/박스 + 치수)
        ▼
[매니저 — 그리기 서비스, 데미지 없음]
   풀에서 슬롯 하나 재사용 → 셰이더에 모양·색 세팅
   매 프레임 fill = (지금-시작)/지속 → 빨간 게 차오름
        ▼
[타격 순간]
   완료 → fill 100% 스냅 → "꽉 참 = 타격" 플래시 → 반납
   같은 모양 데이터의 Contains(원점, 회전, 플레이어)로 판정
        ▼
[플레이어]
   장판 안 → 타격 (+ 보스면 넉백) / 회피·무적 → 데미지도 넉백도 무효
```

## 정리

세 가지 조건이 세 가지 설계로 그대로 이어졌습니다.

- **보이는 범위 = 맞는 범위** → 그리기와 판정이 같은 모양 데이터 하나를 공유.
- **타이밍 튜닝 하기 싫다** → 타격 순간 완료 호출로 꽉 참을 강제.
- **모바일에서 가벼워야** → 쿼드 풀링 + MaterialPropertyBlock으로 런타임 할당·머티리얼 인스턴스 제로.

그리고 이 셋 위에 그리는 서비스와 때리는 주체를 분리한 덕에 디자이너는 코드 0줄로, 보스는 코드로 정밀하게 **같은 파이프라인을 두 결로** 썼습니다.

한 줄로 요약하면 하나의 모양 데이터로 그리기와 판정을 묶어 "보이는 게 곧 맞는 것"을 보장하고, 타격 순간 채움을 강제 완료해 타이밍 튜닝을 없앴으며, 전부 풀링으로 재활용해 모바일에서 공짜에 가깝게 만든 예고장판 시스템입니다.

## 1. 배경 — 색을 정하는 곳과 볼 수 있는 곳이 달랐습니다

먼저 램프맵은 **가로로 긴 그라데이션 한 줄짜리 이미지**입니다. `128 x 1` 픽셀의 가로로 한 줄뿐인 텍스처입니다. 왼쪽 끝이 빛을 못 받는 그늘 색이고 오른쪽으로 갈수록 밝아집니다.

셰이더는 픽셀마다 빛을 얼마나 받는지를 계산한 다음 **그 밝기로 램프의 가로 위치를 정해 색을 꺼냅니다.** 그늘이면 왼쪽 색을 밝으면 오른쪽 색을 씁니다. 빛의 세기를 색으로 바꿔 주는 변환표라고 보면 됩니다. 툰 셰이딩에서 그늘이 검정이 아니라 붉거나 푸른 색조로 떨어지는 것이 이 표 때문입니다.

```
램프 한 장 = 128 x 1 픽셀

   그늘 ────────────────────────▶ 빛
   [ 어두운 색조 ][ 중간색 ][   흰색   ]
              ▲
     이 픽셀이 이만큼 밝다 → 여기 색을 쓴다
```

그런데 표가 하나뿐이면 몸도 머리카락도 눈도 전부 같은 색조로 떨어집니다. 부위마다 다른 표를 쓰게 하려고 **인덱스 맵**을 씁니다. 캐릭터 텍스처와 같은 자리에 맞춰 놓은 흑백 그림인데 부위마다 정해진 회색값으로 칠해 둡니다. 셰이더는 픽셀을 그릴 때 이 그림에서 회색값을 읽고 **몇 번 표를 쓸지** 정합니다.

```
인덱스 맵의 회색값        쓰는 램프
    0   몸        →    0번
    84  머리카락   →    1번
    128 눈        →    2번
```

여기에 한 가지가 더 붙습니다. **표 한 장이 아니라 두 장이 한 쌍**입니다. 하나는 곱하는 표로 그늘의 색조를 정하고 다른 하나는 더하는 표로 피부가 붉게 비쳐 보이는 느낌을 얹습니다. 곱셈만으로는 어두운 곳을 밝게 만들 수 없어서 더하는 쪽이 따로 있습니다. 안 쓰는 부위는 검정을 넣어 두면 아무 일도 일어나지 않습니다.

그래서 **부위가 6개면 램프는 12장**이 됩니다.

문제는 이 12장을 만드는 과정이었습니다. 아티스트는 포토샵에서 `128×1` 픽셀짜리 그라데이션을 한 장씩 그리고 곱·덧 순서와 `_MaxRampIndex` 계수 그리고 압축 설정 같은 규칙을 직접 맞춰야 했습니다. 인덱스 맵의 회색값도 셰이더 공식이 나누는 칸 안에 정확히 들어가야 하는데 이건 눈에 보이지 않는 정보라 맞는지 틀리는지 알 방법이 없었습니다.

그리고 더 근본적인 문제가 있었습니다. **아트 컨펌은 3ds Max에서 납니다.** 그런데 Max에서 쓰는 DirectX Shader는 텍스처 배열을 읽지 못합니다. 그래서 Max 뷰포트에서는 인덱스별로 다른 램프가 적용된 모습을 볼 수가 없었고 색 하나를 바꾸려면 유니티까지 넘어가서 확인하고 다시 돌아오는 왕복이 계속 생겼습니다.

## 2. 먼저 잰 것 — 램프 236장을 전부 분석했습니다

툴을 어떤 방식으로 만들지 정하기 전에 프로젝트에 이미 들어 있는 램프 236장을 전부 열어 봤습니다. 감으로 "그라디언트 위젯이면 될 것 같다"고 말하는 것과 숫자를 들고 말하는 것은 다르다고 봤습니다.

| 항목 | 결과 |
|---|---|
| 램프 PNG | **236장 전부 `128×1`** |
| 바이트까지 완전히 동일 | 126종 |
| 눈으로 구분 불가 — 최대 채널차 8 이하 | 125종 |
| 실제로 의도된 색 차이 | **20종 수준** |
| 밝은 끝이 흰색 | 227장 · 96% |

곡선 모양은 색을 빼고 보면 42종이었고 공통 형태가 있었습니다. 앞쪽 40%가 그늘로 평평하다가 중간에서 급격히 흰색으로 올라가는 모양입니다. 툰 셰이딩의 "경계"가 그 지점입니다.

여기서 방향이 정해졌습니다. **포토샵에서 그릴 필요가 없다.** 형태가 거의 같고 색만 다르다면 에디터 안의 그라디언트 편집기로 충분히 만들 수 있습니다.

다만 중간에 한 번 틀렸습니다. 처음에는 "그늘 색에서 흰색으로 가는 2색 보간이면 재현되겠다"고 보고 실제로 맞춰 봤는데 오차 8 이내로 재현되는 것이 30%뿐이었습니다. 램프가 중간 색조를 한 번 거치기 때문입니다. 그래서 색 세 개와 슬라이더로 모양을 만드는 방식을 버리고 **개수 제한이 없는 마커 + 마커마다 보간 방식을 고르는 구조**로 갔습니다.

![목록의 띠를 누르면 뜨는 편집 창입니다. 바를 더블클릭하면 그 자리에 마커가 생기고 마커마다 보간 방식을 따로 고릅니다. 색 세 개와 슬라이더로 모양을 만들던 방식을 이걸로 바꿨습니다.](img/20-ramp-tool/fig02-ramp-editor.png)

## 3. 설계 — 툴을 Max에 두고 안 보이던 정보를 눈에 보이게 했습니다

컨펌이 Max에서 나므로 툴도 Max에 있어야 한다고 봤습니다. 동선은 이렇게 잡았습니다.

```
1. 창에 인덱스 텍스처를 넣는다
2. 넣는 즉시 인덱스 개수를 검출하고 128 x N 아틀라스를 굽는다
3. 각 인덱스에 빨강·주황·노랑·초록·파랑·보라를 자동으로 넣는다
4. 머티리얼에 연결하면 뷰포트에 부위별 색이 그대로 보인다
5. 램프를 편집하면 그 줄만 다시 구워 뷰포트가 즉시 바뀐다
```

3번이 이 툴에서 제일 마음에 드는 부분입니다. 지금까지 인덱스는 눈에 안 보이는 정보였습니다. 자동으로 구분색을 넣으면 **모델을 보는 순간 어디가 몇 번인지 바로 보입니다.** 순서를 정하는 노동도 사라집니다. 인덱스 맵이 이미 순서를 가지고 있으니 아티스트는 "이 부위에 이 색" 만 보면 됩니다.

이 기능은 나중에 예상 못 한 곳에서 한 번 더 쓰였습니다. 아틀라스 줄 순서가 맞는지 검증할 때 부위마다 무지개 순서대로 색이 나오는지만 보면 됐습니다. 원래 아티스트 편의를 위해 만든 기능이 그대로 검증 도구가 됐습니다.

설계 전에 기술적 관문을 하나 확인했습니다. "PNG를 덮어쓰면 Max 뷰포트가 갱신되는가"입니다. 이게 안 되면 실시간 편집이라는 전제 자체가 무너지므로 먼저 실험 스크립트로 확인했습니다. 결과는 통과였고 파일 변경 자동 감지에 맡기지 말고 저장 직후 `reload()`를 직접 불러 주면 눈에 띄게 빨라진다는 것까지 확인했습니다.

![편집 창에서 색을 바꾸면 뷰포트가 바로 따라옵니다. 왼쪽이 색을 고르는 중이고 오른쪽이 적용된 결과입니다. 유니티로 넘어가지 않고 여기서 색을 정합니다.](img/20-ramp-tool/fig04-viewport-compare.png)

## 4. 색이 안 맞습니다 — 감마가 두 군데서 걸려 있었습니다

툴을 만들고 나서 아티스트가 포토샵에서 쓰던 색과 비교했는데 맞지 않았습니다. 원인을 찾는 데 제일 오래 걸렸습니다.

먼저 계산값 자체를 재 봤더니 `(140, 83, 163)`으로 포토샵에서 찍은 값과 사실상 같았습니다. 계산은 처음부터 맞았던 것입니다. 문제는 그 값을 **Max가 화면에 그릴 때와 파일로 쓸 때 각각 한 번씩 더 밝게 만든다**는 점이었습니다.

| 경로 | 원인 | 결과 |
|---|---|---|
| 파일 | 전역 `fileOutGamma = 2.2` | `194, 153, 208` |
| 화면 | `imgTag` 컨트롤이 자체적으로 `^(1/2.2)` 를 씌움 | `194, 154, 210` |

두 지수가 정확히 `1/2.2`였습니다. 여기서 걸린 함정은 **Max의 감마 설정값을 봐도 이걸 알 수 없다**는 것입니다. `displayGamma` 전역값도 색 관리 대화상자도 `1.0`인데 화면 컨트롤은 그것과 무관하게 감마를 씌웁니다. 설정을 읽지 말고 화면을 캡처해서 직접 스포이드로 찍어야 알 수 있었습니다.

그 뒤로는 색이 이상하면 세 군데를 갈라서 봅니다. 먼저 비트맵 픽셀값을 직접 재서 계산이 맞는지 보고 저장한 PNG를 외부 프로그램으로 열어 파일 감마를 확인하고 마지막으로 화면을 캡처해 스포이드로 찍어 화면 감마를 봅니다. 세 값이 다르면 원인도 각각 다른 것이고 하나로 뭉뚱그리면 못 찾습니다.


## 5. 색을 섞는 방식 — RGB로 섞으면 중간이 탁해집니다

램프는 마커와 마커 사이를 코드가 채워서 만듭니다. 그 사이를 어떤 방식으로 채우느냐가 색을 정합니다.

처음에는 RGB 값을 그대로 섞었습니다. 그런데 빨강에서 파랑으로 가는 램프를 만들어 보니 가운데가 탁하게 죽었습니다. 아티스트가 포토샵에서 만든 것과 눈에 띄게 달랐습니다.

![왼쪽이 3ds Max의 기본 그라디언트이고 오른쪽이 포토샵입니다. 같은 두 색을 썼는데 왼쪽은 가운데가 탁한 보라로 죽고 오른쪽은 채도를 유지합니다.](img/20-ramp-tool/fig09-rgb-vs-oklab.png)

원인은 RGB의 세 축이 **색과 밝기를 같이 들고 있다**는 데 있습니다. 빨강 `(255, 0, 0)`과 흰색 `(255, 255, 255)`을 섞으면 초록과 파랑이 같이 올라갑니다. 중간으로 갈수록 채도가 떨어져 탁해지는 것이 이 때문입니다.

포토샵은 OKLab으로 섞습니다. OKLab은 축을 **밝기 하나와 색조 둘**로 나눠 둔 색 공간이라 섞어도 밝기와 색조가 서로를 밀지 않습니다.

여기에 사람 눈 이야기가 붙습니다. 눈 안에는 긴 파장과 중간 파장 그리고 짧은 파장에 반응하는 원추세포 세 종류가 있습니다. 그리고 빛의 양이 8배가 되어도 8배 밝다고 느끼지 않습니다. 실제 값이 `1 → 8 → 27`로 갈 때 사람은 `1 → 2 → 3`으로 느낍니다. 세제곱 관계입니다. OKLab은 이 관계를 세제곱근으로 넣어 계산합니다.

그래서 변환은 네 단계가 됩니다.

- 화면에 찍힌 값을 실제 빛의 양으로 되돌린다
- 빛의 양에서 원추세포 세 종류에 해당하는 값을 구한다
- 세제곱근을 씌워 사람이 느끼는 정도에 맞춘다
- 밝기 하나와 색조 둘이 나온다

원저자가 공개한 공식을 그대로 옮겨 램프 굽는 코드에 넣었습니다.

![결과입니다. 왼쪽이 Max 기본 그라디언트이고 오른쪽 위가 포토샵 아래가 툴에 넣은 OKLab 보간입니다. 포토샵과 같은 색으로 떨어집니다.](img/20-ramp-tool/fig10-oklab-result.png)

그런데 옮겨 적으면서 계수 하나의 부호를 빠뜨렸습니다. 증상은 순수한 빨강을 넣으면 파랑이 11만큼 섞여 나오는 것이었습니다. 당시에는 이걸 "OKLab 왕복 오차의 한계"라고 설명하고 넘어갈 뻔했는데 원저자 C++ 코드를 나란히 놓고 한 글자씩 대조해서 발견했습니다. 코드 리뷰도 못 잡았던 종류라 외부 공식을 옮길 때는 원본과 직접 대조해야 한다는 것을 여기서 배웠습니다.

## 6. 툴이 시킨 대로 했더니 작업물이 사라졌습니다

실사용 단계에서 나온 문제입니다. 인덱스 텍스처를 지정하면 편집하던 램프 목록을 **무조건** 비우게 해 뒀었습니다. 평소에는 맞습니다. 다른 인덱스 맵을 넣었다면 기존 램프는 의미가 없으니까요.

그런데 정반대인 동선이 두 개 있었습니다. 하나는 저장해 둔 파일만 불러와서 인덱스 칸이 비어 있을 때 **툴이 알려준 파일명을 찾아 채워 주는 경우**이고 다른 하나는 불일치 경고가 떠서 **툴이 "맞는 인덱스 맵을 지정하세요"라고 시켜서 지정하는 경우**입니다. 둘 다 램프가 유효해지는 순간인데 오히려 지워 버렸고 되돌릴 방법도 없었습니다.

고친 방식은 판정 기준을 바꾼 것입니다. "파일을 골랐나"가 아니라 **"내용이 맞나"**로 봅니다.

```maxscript
if (rtRampsMatchIndexValues rtRampData rtIndexValues) then
    showRampList()          -- 같은 세트다. 램프도 클립보드도 살린다
else
(
    rtRampClipboard = undefined
    refreshRampList #()     -- 다른 세트다. 예전과 같이 비운다
)
```

저장 버튼이 쓰는 것과 같은 함수로 판정합니다. 개수뿐 아니라 인덱스 값까지 비교하므로 "우연히 개수가 같아서 통과"하는 경우는 없습니다.

같은 종류의 실수가 머티리얼 쪽 입구에도 있었습니다. 대상이 맞는지 확인하려고 `[지정]` 버튼을 눌렀을 뿐인데 같은 머티리얼인지 비교하지 않고 목록을 비우고 있었습니다. 한 줄로 해결됐습니다.

여기서 판별 기준을 하나 정해 뒀습니다. **바뀐 게 없는데 지우면 버그고 바뀌어서 지우면 정상입니다.** 서브머티리얼 드롭다운을 바꿀 때 목록을 비우는 것은 대상이 실제로 바뀌는 자리라 그대로 뒀습니다.

## 7. 반쯤 성공한 상태를 남기지 않았습니다

저장 파일을 불러올 때 머티리얼을 씬에서 못 찾는 경우를 처음에는 부드럽게 처리했습니다. 칸에 "씬에서 못 찾음"이라고만 적고 램프는 그대로 불러왔습니다. **틀린 판단이었습니다.**

머티리얼에 연결까지 되어서 바로 수정하는 것이 이 툴의 목적인데 머티리얼이 없으면 편집해도 뷰포트에 안 보입니다. 게다가 그 상태로 저장하면 배선 정보가 빈 값으로 덮여 조용히 사라집니다. 화면에는 램프가 멀쩡히 떠 있는데 실제로는 아무것도 할 수 없는 상태가 제일 나쁩니다.

그래서 불러오기를 **하드 실패**로 바꾸고 순서도 같이 정리했습니다.

```
파일 고르기 → 파싱 → 머티리얼 찾기 ← 여기서 실패하면 중단. 화면은 그대로
           → "목록이 사라집니다" 확인 → 적용
```

옛 코드는 램프를 다 앉힌 **뒤에** 머티리얼을 만졌습니다. 그러면 실패했을 때 이미 목록이 날아간 뒤입니다. 검사가 먼저이고 화면 변경이 나중입니다. 실패할 걸 알면서 먼저 묻지 않도록 확인 대화상자도 검사 뒤로 내렸습니다.

![대상 머티리얼이 제대로 물리면 연결됨 뒤에 실제 파일 이름이 뜹니다. 이 표시가 없으면 편집해도 뷰포트에 안 나타나므로 지금 어디에 연결돼 있는지가 항상 보여야 합니다.](img/20-ramp-tool/fig03-material-connect.png)

## 8. 드래그하는 동안 뷰포트가 따라오게 — 26ms에서 5ms로

마커를 끄는 동안 색이 실시간으로 따라오게 만들려니 굽는 비용이 걸렸습니다. 추측하지 않고 나눠서 쟀습니다.

| 항목 | 시간 |
|---|---|
| 전체 아틀라스 굽기 12줄 | 26.0 ms |
| ├ 색 계산 | **22.65 ms · 89%** |
| └ PNG 저장 | 2.7 ms |
| 사본을 떠서 한 줄만 고치기 | 19.8 ms |
| **메모리에 올려두고 한 줄만 고치기** | **4.95 ms** |

색 계산이 89%였습니다. 마커 하나를 움직이면 실제로 바뀌는 것은 그 램프 한 줄뿐인데 12줄을 전부 다시 계산하고 있었던 것입니다. 그래서 드래그를 시작할 때 전체를 한 번 구워 메모리에 올려 두고 움직이는 동안에는 그 줄만 고쳐 저장합니다.

전역에 비트맵을 들고 있으면 누수가 걱정되는데 **수명을 드래그 제스처 하나에 묶어서** 해결했습니다. 버튼을 누를 때 만들고 뗄 때 해제하며 편집 창이 닫힐 때도 같은 해제를 부릅니다. 드래그 중에는 마우스가 위젯에 잡혀 있어 램프 개수가 바뀔 수 없으므로 복잡한 무효화 로직도 필요 없었습니다.

이 과정에서 실패가 조용히 묻히는 함정도 하나 잡았습니다. 아래 계층에서 이미 예외를 잡아 `false`로 바꿔 올려보내는데 위에서는 예외만 기다리고 반환값을 안 보고 있었습니다. 그래서 파일 잠김으로 계속 실패하는데도 화면에 아무 표시가 안 떠서 엉뚱한 곳을 봤습니다. **실패가 예외로 오는지 반환값으로 오는지부터 확인해야 합니다.**

## 9. 셰이더 이식 — 기존 코드는 3줄만 고쳤습니다

Max 뷰포트에 색을 보여주려면 `HeroToon.fx`가 인덱스 램프를 읽을 수 있어야 했습니다. 다만 상부가 이 fx를 다시 짤 예정이라 승인 범위가 "램프 곱/덧만 동작하게"로 정해져 있었습니다. 최종본을 만드는 게 아니라 **이렇게 하면 된다는 증명**을 만드는 작업이었습니다.

그래서 유니티 셰이더의 램프 경로만 골라 읽었습니다. 719줄 중 램프에 닿는 것은 60줄 정도라 "이 줄이 최종 색에 어떤 경로로 들어가나"를 기준으로 따라가고 안 닿으면 이름만 알고 넘어갔습니다. 그 결과를 줄 번호까지 적은 이식 목록으로 만든 다음 옮겼습니다.

결과는 636줄에서 690줄이 됐고 **기존 코드에서 고친 것은 두 군데 3줄**입니다. 램프 로직 전부를 함수 하나에 넣어서 나중에 fx를 다시 짤 때 그 함수만 들어내면 되게 했습니다. 교체한 원본은 지우지 않고 주석으로 남겼습니다.

이식하면서 걸린 것이 두 가지입니다.

하나는 **fx에 Point 샘플러가 없다**는 점입니다. Linear 3종뿐이라 인덱스 맵을 그대로 읽으면 부위 경계에서 값이 보간돼 엉뚱한 인덱스가 나옵니다. 유니티는 셰이더가 `sampler_PointClamp`를 직접 지정해서 아티스트가 임포트 설정을 잘못해도 안전한데 fx에는 그 안전장치가 없어서 직접 선언해야 했습니다.

다른 하나는 주소 지정 방식이었습니다. 처음에 Clamp로 넣었는데 fx 파일 안에 이런 주석이 있었습니다.

```hlsl
// Because the y of texture UV is start from -1 to 0 in 3dsMax
lineUV.y = lineUV.y + 1;
```

3ds Max에서는 UV의 y가 `-1`에서 `0`으로 갑니다. 보정 없이 Clamp를 쓰면 음수가 전부 `0`으로 눌려서 **모델 전체가 인덱스 맵의 맨 윗줄만 읽게** 됩니다. Wrap으로 바꾸니 `0~1`이든 `-1~0`이든 양쪽 다 맞았습니다.

![fx 이식이 끝난 뒤의 화면입니다. 저장 완료 뒤에 파일 이름이 뜨고 목록에서 정한 색이 캐릭터에 그대로 올라와 있습니다. fx가 아틀라스를 인덱스별로 나눠 읽고 있다는 뜻입니다.](img/20-ramp-tool/fig05-save-done.png)

## 10. 유니티 임포터 — 한 줄만 찍어봤으면 못 잡았을 것

Max에서 저장하면 아틀라스 PNG 한 장과 JSON 한 개가 나옵니다. 유니티 쪽은 이걸 12장으로 잘라 임포트 설정을 박고 `Texture2DArray`로 조립합니다.

여기서 설계 원칙을 하나 정했습니다. **유니티는 색을 만들지 않습니다.** 아트 컨펌이 Max에서 나는데 유니티에서 그림이 달라지면 컨펌이 무의미해집니다. 그래서 유니티 쪽에는 색 피커도 슬라이더도 그라디언트 위젯도 넣지 않았습니다. 미리보기가 있지만 편집용이 아니라 "Max에서 본 그거랑 같나" 확인용입니다. 실험용으로 만들어 뒀던 유니티 램프 편집 창은 지웠습니다.

제일 위험했던 곳은 **세로축 방향**이었습니다. PNG는 맨 위가 첫 줄인데 유니티 `Texture2D`는 아래가 `y=0`입니다. 그냥 읽으면 12줄이 통째로 뒤집혀서 0번 인덱스가 5번의 램프를 쓰게 되는데 **색이 다 나오기 때문에 화면만 봐서는 못 잡습니다.**

그래서 한 줄만 찍어보지 않고 12줄을 전부 대조했습니다. 아틀라스 왼쪽 끝 픽셀이 각 램프의 첫 마커 색이라 JSON과 1:1로 맞춰볼 수 있었습니다.

```
뒤집힘(y = height-1-row) 일치 : 12 / 12
그대로(y = row)          일치 :  0 / 12
```

흥미로운 것은 **같은 파일을 읽는데 fx 쪽은 뒤집을 필요가 없었다**는 점입니다. 읽는 주체가 다르면 축도 다릅니다. Max/유니티 좌표계 차이는 이 프로젝트에서 이미 전례가 있었습니다. 매트캡 UV의 y를 fx만 뒤집어 쓰고 있었고 그 주석이 힌트가 됐습니다.

조립 단계에서도 한 번 막혔습니다. 배열 에셋은 정상으로 만들어지는데 인스펙터의 텍스처 목록이 비어 있었습니다. 에러도 경고도 없었습니다.

```csharp
arrayImporter.Textures = slices;   // 프로퍼티에 대입해도 dirty 표시가 안 붙는다
arrayImporter.SaveAndReimport();   // 저장할 게 없다고 보고 옛 설정으로 재임포트
```

유니티 내장 임포터는 프로퍼티를 건드리면 변경 표시를 찍어 주지만 `ScriptedImporter`의 평범한 C# 필드는 아무도 찍어 주지 않습니다. `SerializedObject`로 써야 했습니다. 이런 종류는 눈으로 확인하다 놓치기 쉬워서 만든 뒤 배열을 되읽어 크기·포맷·깊이를 보고하게 붙였습니다.

![유니티 쪽 임포터입니다. JSON 경로를 넣으면 캐릭터 이름과 인덱스 6개 · 슬라이스 12개 · 128 x 12 가 확인용으로 뜨고 아래에 잘라낼 램프 띠가 전부 그려집니다. 만들기를 누르기 전까지는 파일을 하나도 쓰지 않습니다.](img/20-ramp-tool/fig06-unity-importer.png)

![만들기를 누르면 램프 12장이 이름 규칙대로 생기고 배열로 묶여 머티리얼에 물립니다. 오른쪽 인스펙터의 Ramp Map Array 가 조립된 배열입니다.](img/20-ramp-tool/fig07-unity-assets.png)

마지막으로 아티스트 제보를 하나 반영했습니다. Max에서 뽑은 파일이 아트팀이 쓰던 것과 포맷이 다르다는 것이었는데 재 보니 사실이었습니다. MAXScript의 PNG 저장 기본값이 16비트 RGBA라 지정을 안 하면 그대로 나갑니다. 8비트 RGB로 맞추니 **4,478바이트가 526바이트**가 됐고 덤으로 알파 채널이 사라지면서 예전에 겪었던 알파 누수 문제가 원천 차단됐습니다.

## 11. 결과와 한계

```
램프 툴에서 마커 편집 → 아틀라스 자동 굽기 → Max 뷰포트 색이 즉시 바뀜
                                        → 저장 → 유니티에서 버튼 하나로 배열 조립
```

![Max에서 정한 색이 유니티 씬까지 그대로 올라온 상태입니다.](img/20-ramp-tool/fig08-unity-scene.png)

원래 목표였던 "아티스트가 Max에서 보면서 램프를 정한다"가 동작합니다. 아티스트가 알아야 할 것은 **인덱스 맵과 색**뿐이고 번호 규칙·페어 순서·계수·임포트 설정은 툴이 흡수합니다. 조립된 배열은 기존 배열과 크기·포맷·`graphicsFormat`·서브오브젝트 ID까지 같은 것을 실측으로 확인했습니다.

솔직하게 남은 것도 적어 둡니다.

- **줄 순서를 매번 검증하지는 않습니다.** 픽셀 대조는 "PNG로 쓰고 읽는 사이에 색이 안 변했다"까지만 보증합니다. 줄 순서가 맞다는 것은 개발 중 12줄을 전수 대조한 1회 결과이고 아틀라스 규칙이 바뀌면 조용히 틀릴 수 있습니다. 이건 문서에 그대로 적어 뒀습니다.
- **머티리얼에 자동으로 꽂는 것은 만들지 않았습니다.** 배열·인덱스 맵·계수 셋을 언제 어느 머티리얼에 넣을지 판단이 계속 늘어나는데 인스펙터에서 끌어다 놓으면 끝나는 일입니다. Max 툴에서 연결을 수동 버튼으로 둔 것과 같은 판단입니다.
- **fx 이식은 승인 범위가 램프까지입니다.** 해칭 노이즈를 만드는 방식이 유니티와 fx가 통째로 달라서 노이즈를 켜면 경계 부분이 다르게 보입니다. 색을 비교할 때는 꺼야 한다는 것을 아티스트가 알아야 합니다.

이 작업에서 얻은 것 중 기술보다 오래 남을 것은 태도 쪽입니다. **이론으로 설명하려다 세 번 틀렸습니다.** 감마를 설정값으로 판단했다가 틀렸고 OKLab 오차를 이론적 한계로 설명하려다 틀렸고 코드 리뷰 결과를 실행 없이 받아들였다가 두 번 틀렸습니다. 그래서 값이 예상과 다르면 화면에 직접 찍어보는 것을 규칙으로 정해 두고 진행했습니다.
